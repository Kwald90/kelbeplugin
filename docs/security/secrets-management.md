## Rules

1. One `.env` per environment, `deploy/<env>/.env`, owned by root, mode 600, created on the host by
   `init-env.sh` (which refuses to overwrite). Production values are generated on the production
   host and never copied from staging. Planned: move `.env`, `backup.conf` and
   `backup-recipients.txt` out of the git checkout to `/etc/fishtape/<env>/`, so a commit can never
   replace them (threat model TM-STG-01).
2. Containers get only what they need. The compose files blank the raw role passwords inside app
   containers and pass only connection URLs; the owner URL goes only to `migrate` (and `seed` on
   staging); the HQ URL only to `hq-api`. Every server container still reads the whole `.env`
   through `env_file`, so `SECRETS_MASTER_KEY` and the OAuth secrets reach `hq-api` and `worker`
   too; trim that per service when the API's needs are known.
3. Never in git, CI logs, pull requests, issues, chat with AI agents, email, screenshots or support
   tickets. AI agents get `.env.example` values and seeded data, never real secrets.
4. Never on a command line, where shell history and `ps` can see it. Use env files, files with
   mode 600, or stdin (`restore-test.sh --identity -` pipes the age key over SSH and never writes
   it to the server's disk).
5. Never logged. The API's logger must redact `authorization`, `cookie`, `x-api-key`, `password`,
   `pin`, `token` and `secret` fields, and never log request bodies (TM-LEAK-06).
6. Shown once, masked after. A tenant secret or API key is visible only when entered or created;
   afterwards the UI shows a masked form (for example the last four characters) and offers
   "replace", never "reveal".
7. CI secrets live only as GitHub environment secrets used by the deploy jobs. GitHub masks them
   in logs; don't add `set -x` to steps that handle them. The deploy key file is deleted at the
   end of each job.
8. The password manager holds: each environment's `SECRETS_MASTER_KEY` copy, the age private
   keys, passphrases for admin SSH keys, every console login, and the recovery codes for those
   accounts.

## Generating secrets

```bash
openssl rand -hex 32        # Postgres role passwords: 64 hex characters, safe inside connection URLs
openssl rand -base64 32     # SECRETS_MASTER_KEY: 32 random bytes, base64
age-keygen -o fishtape-<env>-backup.key                                  # on your own computer
ssh-keygen -t ed25519 -N '' -C github-actions-<env> -f fishtape-<env>-ci   # deploy key
```

In code, tokens, API key secrets and recovery codes come from `crypto.randomBytes(32)` (encoded
as base64url), never `Math.random`. Record ids are not secrets (`store.js` falls back to
`Math.random` for ids when `crypto.randomUUID` is missing) and must never be used as one, for
example as a share-link token.

## Envelope encryption for tenant secrets

The contract fixes the outline: `tenant_secrets` uses AES-256-GCM, envelope-encrypted with
`SECRETS_MASTER_KEY`. The details below are the recommended design; workstream A confirms them
in `docs/architecture/`.

- Each secret gets its own random 32-byte data key. (One data key per tenant also works; per
  secret limits the damage of any single mistake.)
- The secret is encrypted with AES-256-GCM under the data key, with a fresh random 96-bit nonce
  and additional authenticated data of tenant id, secret name and key version. A ciphertext copied
  into another tenant's row then fails to decrypt.
- The data key is wrapped (AES-256-GCM, its own nonce) with the master key.
- Each row stores: ciphertext, nonce and tag; the wrapped data key with its nonce and tag;
  `kek_id` (which master key wrapped it, for example `k1`); a version; created and rotated times;
  who set it; the last four characters for display.
- Plaintext exists only in memory while calling the vendor. Never in logs, error messages, job
  payloads, audit summaries or responses to the browser.
- A decryption failure is logged as an event with the secret id and `kek_id`, never the value.

## Master key rotation

The contract has one `SECRETS_MASTER_KEY`. Rotating without downtime needs the API to accept a
second, decrypt-only key, each with an id (proposed addition to the contract:
`SECRETS_MASTER_KEY` plus `SECRETS_MASTER_KEY_PREVIOUS`). Then:

1. Generate a new key (`openssl rand -base64 32`) and store it in the password manager.
2. Make it the active key (`k2`) and set the old one as previous (`k1`); restart `api` and
   `worker`. New secrets are wrapped with `k2`; reads unwrap with whichever key the row's
   `kek_id` names.
3. Run the re-wrap job: for every row with `kek_id = k1`, unwrap the data key with `k1`, wrap it
   with `k2`, update `kek_id`. The secret ciphertexts don't change, so this is quick.
4. Confirm no rows still use `k1`. Remove the previous key from `.env` and restart.
5. Keep `k1` in the password manager until every backup that still holds `k1`-wrapped rows has
   aged out (about 8 weeks), because restoring one of them needs `k1`. Then destroy it.
6. If `k1` leaked (rather than routine rotation), also ask the affected tenants to roll their
   vendor keys: anyone holding `k1` and an older copy of the database can read the old values.

Practise on staging before doing it in production.

## When a secret leaks

1. Rotate first, investigate second. Revoke or replace the secret at its source using
   [docs/runbooks/rotate-secrets.md](../runbooks/rotate-secrets.md).
2. Work out the scope from the blast-radius column: which environment, what it can reach, since
   when it was exposed.
3. Look for use: vendor dashboards and logs, `audit_events`, Postgres logs (production logs
   connections), nginx logs, the GitHub security log.
4. If it reached git: rotating is the fix. The repo is public, so assume it was copied the moment
   it was pushed (forks, caches, scrapers). Cleaning history afterwards is tidying, not a remedy.
5. GitHub secret scanning alerts: close them as "revoked" only after rotating. If push protection
   blocked the push, follow [secure-sdlc.md](secure-sdlc.md#secrets-never-in-code).
6. If customer data or a tenant's vendor account may have been reached, it is an incident:
   [docs/runbooks/incident-response.md](../runbooks/incident-response.md) (SEV2 for a suspected
   breach, SEV1 for a confirmed or likely one). For a tenant's own key, tell the tenant and help
   them roll it at the vendor.
7. Write down what happened and change something so it doesn't happen again (a gitleaks rule, a
   redaction entry, a checklist line).
